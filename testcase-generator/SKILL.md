# 游戏测试用例生成 Skill

仅适用于休闲、卡牌、SLG、RPG、FPS、模拟经营等游戏项目。非游戏业务请使用 `case-design` skill。本 Skill 默认生成中文、自然易读、可人工执行的 Markdown 用例；Excel 仅在用户明确要求时导出。用户要求保存到飞书时，适用下方“飞书交付规则”。

## 核心标准

- 标题、前置条件、测试数据、步骤、预期结果同步具体化，直接写对象、条件、动作和可观察结果；不强制 `[主语]应[行为]` 或维度标签。
- 预期结果必须可由界面、文字、数值、状态、流水、接口反馈、动效、音效或震动判定；未定义规则写 `待确认：……`，不得编造。
- 步骤使用 `1.`、`2.` 等数字编号，通常 1～3 步；实际结果生成时留空，结果默认 `未执行`。
- 规范细节以 `references/writing_guide.md` 为唯一事实源，数据取值以 `references/test_data_dictionary.md` 为准。

## 工作流程

### 0. 输入与规模

1. `.md` 需求直接读取；`.docx`、`.doc`、`.pdf`、`.txt` 先用 `scripts/convert_to_md.py` 转换。
2. 解析模块、玩法规则、状态交叉、边界异常和用户指定规模后定档：轻量 ≤20 条（1～2 模块，每模块 3～8 条）；标准 ≤50 条（2～4 模块，每模块 5～15 条）；完整不限总数（每模块通常 ≤20 条）。
3. 用户已明确“轻量/少量”或明确给出不超过 20 条的目标时，轻量档直接生成；否则先向用户确认档位与预计数量。标准/完整档必须先输出大纲。
4. 若有 `prd-analysis` BR 清单，所有功能性用例建立 `关联BR` 追溯，并在完成后反向检查覆盖。

### 1. 大纲（标准/完整档）

在工作目录写 `00.测试用例大纲.md`，只包含项目档位、模块分组、预估数量、覆盖要点、状态交叉关注点和 BR 覆盖矩阵，不展开详细步骤。

### 2. 分模块生成

按大纲顺序一次生成一个模块，文件名为 `{两位序号}.{模块名}.md`。标准/完整档默认使用 13 列；用户明确轻量且不需要追溯时使用目标十列；有 BR 追溯时使用 13 列或追踪轻量变体。生成中即时按规范合并，轻量/标准/完整单模块分别不超过 8/15/20 条。

### 3. 自检

```bash
python -B scripts/validate.py <md目录> --schema auto
# 明确指定结构时：full / light / light-br / legacy
python -B scripts/validate.py <md目录> --schema full --br-source <prd-analysis.md>
```

修复错误后再交付。`--strict` 仅作为兼容参数，已弃用，不与显式 `--schema` 同用。

### 4. 按需导出 Excel

Markdown 是默认交付物。用户明确要求 Excel 时执行：

```bash
python -B scripts/save_testcases.py <md目录> --output-dir <导出目录>
python -B scripts/save_testcases.py <md目录> --output-dir <导出目录> --template <模板.xlsx> --all-tables
```

导出默认跳过 `00.` 大纲；默认每个文件取第一个表格，`--all-tables` 导出全部表格。模板原有 sheet 和内容会保留，生成的用例 sheet 追加到末尾。

### 5. 飞书交付规则

当用户要求将测试用例保存到飞书时：

1. 默认只创建 **一个汇总飞书电子表格**，不得把大纲和各模块分别创建为多个独立飞书文档。
2. 大纲（适用时）和各功能模块放在同一工作簿中，以不同子 Sheet/Tab 区分；Sheet 名应能直接识别模块，列结构沿用本 Skill 的对应 schema。
3. 中间 Markdown 或本地 Excel 可用于生成和校验，但它们不是多个飞书交付物；最终只交付汇总电子表格链接。
4. 在线写入使用 `lark-sheets` 的导入/工作簿能力，并遵守其样式、类型保真及回读校验规则。写入后至少核验：Sheet 名称与数量、各模块用例行数、用例总数、列数/表头、代表性首尾单元格，以及 `实际结果` 为空、`结果` 默认 `未执行` 等关键字段未错位。
5. 不得自动删除或修改需求源文档、历史用例、参考资料或其他既有文件。若用户要求删除被替代的旧交付物，先用 `lark-drive` 精确列出目标并单独获得明确确认，再执行删除并复查。
6. 本规则仅适用于“保存到飞书”的交付。用户明确要求独立文档、Markdown、本地文件、普通 Excel 或其他格式时，遵循其指定格式，不强制转换为飞书汇总表。

## 输出 schema

完整 13 列：`用例编号｜所属模块｜用例标题｜用例类型｜优先级｜前置条件｜测试数据｜操作步骤｜预期结果｜实际结果｜结果｜关联BR｜备注`

目标十列：`编号｜功能模块｜用例标题｜优先级｜前置条件｜测试数据｜测试步骤｜预期结果｜实际结果｜测试结果`

## 质量检查

- 编号全局唯一且为 `{模块缩写}-{三位数字}`；优先级仅 P0/P1/P2，每模块至少一条 P0，整体 P0 占比默认 ≥30%。
- 正式 schema 的测试数据不可空（无独立数据填 `-`），结果状态合法；预期结果不使用孤立的“正常/正确/无异常”等空泛结论。
- 每条用例看得懂、做得出、能重复、能明确判定；相同前置和同一用户目标可合并，不同准备、独立失败/边界/恢复判定或超过 3 个主要步骤时拆分。
- 状态交叉只回答：状态持续时玩家能做什么及结果；系统自动事件与玩家操作冲突时谁优先；弹层打开和关闭后底层状态如何处理。需求未定义时标注待确认。

## 504 降级

大纲超时则按需求章节拆分；模块超时则拆为子模块；精简过于复杂时先生成初稿，再单独审核。不要在一次调用中生成多个模块。

详细模板见 `references/testcase_template.md`，脚本说明见 `scripts/README.md`。
